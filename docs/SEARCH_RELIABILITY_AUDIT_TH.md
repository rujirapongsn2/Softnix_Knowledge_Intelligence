# ผลตรวจระบบค้นหาและแนวทาง Knowledge Management สำหรับ AI Agent

ตรวจวันที่ 9 กันยายน 2026 จากโค้ดและสถานะ Docker/PostgreSQL ของระบบจริง

## สถานะและขอบเขตหลักฐาน

- ระบบตอบ readiness ผ่าน: database, Redis, Neo4j, LightRAG และ OCR chain
- เอกสารที่ไม่ถูกลบ 100 รายการ: completed 86, failed 14
- ข้อผิดพลาด: RETRIEVAL_ENGINE_BUDGET_EXHAUSTED 7, RETRIEVAL_ENGINE_REJECTED 3, TEXT_EXTRACTION_FAILED 3, EXTERNAL_OCR_TIMEOUT 1
- Auto Metadata: not_started 99, needs_review 1 สถานะ not_started ไม่ได้แปลว่าไม่มี manual metadata หรือทุกเอกสารตั้งค่า extract แล้ว
- ตัวเลขนี้เป็น snapshot และไม่ใช่คะแนน accuracy; ยังไม่มีชุดคำถามจริงที่มีคำตอบและแหล่งอ้างอิงมาตรฐานสำหรับวัดก่อน/หลัง

## สิ่งที่แก้ในรอบนี้

1. ส่ง request deadline ไปยังแต่ละ thread ของ retrieval เพื่อให้ outbound calls เห็นงบเวลาเดียวกับ MCP ไม่ใช่ timeout เริ่มใหม่ในแต่ละ thread ทั้งนี้ไม่ได้รับประกันการยกเลิก SQL หรือทุกขั้นตอนทันทีเมื่อครบ deadline
2. นับ passage ซ้ำภายในช่องทางเดียวเพียงครั้งเดียวใน reciprocal rank fusion ป้องกันผลซ้ำดันอันดับ ขณะที่หลักฐานจากคนละช่องทางยังเสริมอันดับได้
3. ตรวจ index และคะแนน rerank ตัดผลซ้ำ/คะแนนไม่เป็น finite และเติมจากอันดับ fusion เมื่อ provider ส่งกลับไม่ครบ
4. เมื่อ explicit metadata filter ไม่พบเอกสาร ให้จบก่อนเรียกช่องทางค้นหาภายนอก พร้อมเหตุผลใน trace และไม่ผ่อนเงื่อนไขเอง
5. ตั้ง test environment ก่อน import application และแยก retrieval regression จากคิวงานร่วม ทำให้ทดสอบรายส่วนได้

## กระบวนการเป้าหมายที่ใช้ร่วมกันทุกประเภทเอกสาร

อัปโหลด → อ่านข้อความและเก็บแหล่งอ้างอิง → สร้างดัชนีข้อความ/เวกเตอร์ → สกัด metadata แบบงานแยก → ตรวจเฉพาะค่าขัดแย้งหรือไม่มีหลักฐาน → Agent ค้นหาและอ่านหลักฐาน

ให้ document type ใช้กำหนดวิธีอ่านและ schema; ให้ผู้ใช้ตั้งครั้งเดียวต่อประเภท ใช้ metadata เป็น filter เฉพาะข้อจำกัดที่ผู้ใช้ระบุจริง ไม่คาดเดาประเภทแล้วตัดเอกสารออกโดยอัตโนมัติ

การไม่มี metadata ต้องแสดงเป็น unknown ไม่ใช่ไม่มีข้อเท็จจริงนั้น เอกสารยาวที่สกัดได้เพียงบางส่วนต้องคงสถานะ partial การเปลี่ยนต้นฉบับต้องทำให้ค่าที่ AI สกัดจากฉบับเก่าหมดอายุ

## งานถัดไปตามความสำคัญ

1. วัด retrieval ด้วยชุดคำถามที่ตรวจโดยผู้เชี่ยวชาญ ครอบคลุมกฎหมาย งานวิจัย แนวปฏิบัติ ข้อกำหนด และ SOP รวมคำถามที่ตอบไม่ได้และข้อมูลขัดแย้ง วัด recall@k, ความถูกต้องของ citation, การเลือกฉบับ, p50/p95 latency และค่าใช้จ่ายต่อคำถาม
2. ตรวจ 14 เอกสารที่ failed แยกตามสาเหตุ ก่อน retry: กลุ่มงบต้องตรวจ quota/concurrency, กลุ่ม OCR ต้องตรวจไฟล์/วิธีอ่าน การ retry ทั้งหมดโดยไม่แก้สาเหตุจะเพิ่มค่าใช้จ่ายและคิว
3. ตรวจ template ของ 99 เอกสารก่อน backfill ตั้งความหมาย field และหลักฐานที่ยอมรับได้ หลีกเลี่ยงการสกัด field ชื่อทดสอบที่ไม่มีคำอธิบาย
4. ลดการผูกความพร้อมของ document กับ remote graph index: ใช้สถานะความพร้อมแยกแต่ละดัชนี ให้ local evidence พร้อมค้นหาได้เมื่อ remote index มีปัญหา ต้องมี migration, UI status และ regression ด้านสิทธิ์ก่อนเปลี่ยนจริง
5. เพิ่มตัวเลือก passage ก่อน rerank และปรับ snippet ให้ตรงตำแหน่งคำถามหลังมี benchmark ปัจจุบันหลายช่องทางใช้ข้อความ 500 ตัวอักษรแรกและ fusion ตัดก่อน rerank จึงอาจพลาดหลักฐานท้าย chunk
6. ตรวจการค้นหาภาษาไทย: PostgreSQL simple FTS ไม่ตัดคำไทย และ fallback ปัจจุบันทำงานเมื่อ FTS ไม่มีผลเท่านั้น ต้องวัดชุดไทย/อังกฤษก่อนเลือก tokenizer หรือดัชนีเพิ่มเติม

## เกณฑ์เฉพาะประเภท

| ประเภท | ข้อมูลสำคัญ | กรณีทดสอบที่จำเป็น |
| --- | --- | --- |
| กฎหมาย | instrument, มาตรา, วันที่มีผล, amendment/repeal, ฉบับอ้างอิง | มาตราเลขเดียวต่างกฎหมาย, คำถามย้อนหลัง, ฉบับยกเลิก, ข้อยกเว้นข้าม chunk |
| งานวิจัย | ผู้แต่ง, ปี, DOI, วิธีวิจัย, ข้อจำกัด, แหล่งเผยแพร่ | ชื่อใกล้กัน, ผลขัดแย้ง, preprint/ฉบับตีพิมพ์, แยกข้อค้นพบจากข้อเสนอ |
| แนวปฏิบัติ/ข้อกำหนด/SOP | เจ้าของ, รหัส, revision, วันมีผล, ขอบเขต, ผู้อนุมัติ | ฉบับเก่า, เงื่อนไขยกเว้น, หน่วยงานต่างกัน, ขั้นตอนหลายหน้า |

การทดสอบเชิงกลไกในรอบนี้ยังไม่ใช่หลักฐานว่าคะแนน accuracy บนเนื้อหาจริงเพิ่มขึ้นเป็นเปอร์เซ็นต์ใด และยังไม่ได้ backfill หรือ retry เอกสารทั้งคลัง
